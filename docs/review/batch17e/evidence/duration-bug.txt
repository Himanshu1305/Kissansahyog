== (d) which of these explains the 64.5 s ==
- The VOICE FILE is NOT the problem. voice.mp3 is 34.72 s by its header (ID3v2 tag, CBR 64 kb/s, no Xing/VBRI frame, start 0.025 s)
  and 34.66 s when fully decoded (ffmpeg -f null). Speech runs to 34.24 s; the only trailing silence is 0.45 s (34.24 -> 34.69 s),
  under the 0.5 s limit, so no trimming is needed. The admin page's voice player shows ~34.7 s, not 41 s and not 64 s.
  (The founder heard "about 41 s"; the file is 34.7 s long.)
- The MP4 audio stream is 34.69 s (1495 AAC frames, last audio packet starts 34.667 s): the audio is correct.
- The MP4 VIDEO stream is 64.50 s (129 frames at 2 fps, last video packet pts 63.5 s + 0.5 s): this is the whole bug. The container
  duration (64.50 s) follows the longer stream. After 34.69 s there is picture but no sound until 64.5 s.
- Why: the recipe ended the looped still-image input only with `-shortest`. Whether `-shortest` stops a looped image on time depends on the
  ffmpeg version. The CI runner had ffmpeg 8.0.1-3ubuntu2 and let the video run on by about 30 s (one keyframe interval is 30 s).
  Re-running the SAME recipe on the SAME real card and voice here: ffmpeg 6.1.1 -> 34.5 s (correct), ffmpeg 6.0 -> 43.0 s, ffmpeg 7.1 -> 69.5 s.
  The rehearsal in 17E used ffmpeg 6.1.1 and a 40 s tone, the one combination that happens to work, so it never showed the problem.
