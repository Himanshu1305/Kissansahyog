# Batch 15B - backlog and findings

## Findings on the existing MSP data (checked read-only on STAGING; nothing changed; production not read)
1. **Three identical rows per crop.** `msp_prices` on staging has 51 rows, all marketing year 2026-27. Every crop without a "variety" (Wheat 2585, Gram 5875, Masur 7000, Rapeseed & Mustard 5950, Barley 2150, Maize, Moong, Bajra, Groundnut, Sesamum, Nigerseed, Safflower, Sunflower ...) is there 3 times, written on 2026-09-23 at 09:07, 19:12 and 19:57 (three runs of the same insert). Crops with a variety (Paddy, Jowar, Cotton, Soyabean) are there once. Cause: migration 0020 has `unique (crop_en, variety, marketing_year)` but variety is NULL, and in Postgres NULL is never equal to NULL, so the unique rule does not stop a repeat insert. `/msp` is not visibly affected (it uses the first matching row), but a later, different row would silently be ignored. Production was not read; check it before the next MSP load.
2. **Mustard 5950 vs 6200.** `msp_prices` has Rapeseed & Mustard 2026-27 = 5950; the Cabinet table quoted by global-agriculture.com (1 Oct 2026) lists 6200 for 2026-27. Not changed. The official PIB press release of the Cabinet Committee on Economic Affairs (CCEA) for rabi MSP would settle it.
3. **2027-28 rabi MSP is not loaded.** Announced 1 Oct 2026 (wheat 2610, barley 2286, gram 5958, lentil 7390, mustard 6613); `/msp` still shows 2026-27 for crops being sown now. A safe update: insert new rows with marketing_year '2027-28', rabi, `is_active=true`, one per crop (fix the NULL-variety duplicate problem first, for example with a unique index on `coalesce(variety,'')`), and decide which year `/msp` shows. Today `/msp` takes every active row and uses the first match, so old and new rows would clash: the page needs a rule such as "latest marketing_year per crop", or the 2026-27 rows get `is_active=false` at the moment of the switch. The new page does not read the table; it uses the constants in `src/content/kamPani.js`.
