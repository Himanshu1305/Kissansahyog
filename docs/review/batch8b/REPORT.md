## 4. Offline policy as implemented

- **Where:** `src/lib/offline/` — a caching fetch installed on the Supabase **data** client
  (`supabaseClient.js`) and on the direct Open-Meteo call, **only when `isNative()`**, loaded on
  demand. The `supabaseAuth` client is never wrapped. The website never loads it.
- **Allowlist (PUBLIC-CACHEABLE)** — GET tables: mandi_prices, msp_prices, weather_cache_v2,
  listings, listing_unavailable_dates, crops, equipment_types, pincodes, places, village_coordinates,
  articles, cold_storage_public, farm_events, input_prices, kisan_mela, kisan_safalta, kisan_sawaal,
  kisan_sawaal_slug_redirects, page_faqs, procurement_centres, resources, sarkari_yojana,
  site_settings, videos. Read-only RPCs: search_listings, get_public_feedback, recent_crop_reports,
  resolve_active_mela, get_carbon_poll_results, get_carbon_suggestions_public. Host:
  api.open-meteo.com. (Classification in PREFLIGHT.md.)
- **Never stored (PRIVATE / writes)** — profiles, experts (phone numbers), weather_grid_requests,
  get_listing_contact (revealed numbers), get_my_listings, get_my_mela_interests,
  get_availability_nudges, every auth RPC and `/auth/v1/*`, `/storage/v1/*`, every write RPC,
  anything not on the allowlist, any non-200 answer. O1 and O7 test this.
- **Key:** method + full URL + body + the `Accept`, `Prefer` and `Range` headers (maybeSingle() /
  single() change Accept). O1 proves the same URL with a different Accept gives a different entry.
- **Strategy:** network first with a 7 s timeout; on failure / offline the stored copy, if fresh
  enough; each answer from the phone is announced with its stored time (and the data's own time).
  "Offline" = the system's connectivity (@capacitor/network); the WebView's `navigator.onLine` says
  "online" in airplane mode at a cold start. After one failed request the next ones skip the network
  for 20 s. A READ with no usable copy answers a plain **504** at once (postgrest-js retries a thrown
  GET 3× with 1 + 2 + 4 s backoff — that made every offline read cost 7 s); writes still throw, and
  fail at once when the system says offline.
- **Freshness (`src/lib/offline/policy.js`), on the data's own time when it has one:** weather ≤ 24 h
  (`fetched_at`), mandi prices ≤ 7 days (`price_date`), listings ≤ 3 days (stored time), other public
  data ≤ 14 days (stored time). Older → not shown; the "saved information is too old (age)" message.
- **Store:** IndexedDB `ks-offline` v1, cap 5 MB, oldest-first eviction, every storage error
  swallowed. One extra localStorage value: `ks_mandi_latest_date` (the last price date shown — the
  day-change fallback, no extra request).
- **No endless spinners:** in the app a `Spinner` that has run 10 s becomes the offline message with
  "फिर से कोशिश करें"; data sections with no usable data show it directly.
- **Back online:** the page fetches again by itself (1.5 / 6 / 12 s after the system reports a
  connection, while anything on screen is not live); never on form pages (post, signup, login,
  profile, grievance, mela submit, join, admin).
- **Stamp shown on:** home (under the mandi ticker), /mausam, /msp, /browse, listing detail. The
  existing "पिछला भाव (dd/mm)" mandi labels are unchanged; the stamp is extra and only offline.

## 9. Deviations and open issues

Deviations (my decisions — say if you disagree):

1. **Offline reads answer a 504 instead of throwing.** Not in the brief's design; without it every
   offline read cost 7 s, because postgrest-js retries a thrown GET three times. Callers see the same
   `{ data: null, error }` as before. Writes still throw.
2. **The app's offline signal comes from the system** (@capacitor/network), not `navigator.onLine`,
   which says "online" in airplane mode at a cold start. There is also a 20 s "network down" memo
   after one failed request.
3. **Writes fail at once when the system says offline** (before: the WebView needed ~7 s, and while
   it waited the page's other loading stalled — /mausam's weather-grid upsert held the forecast
   back). They still fail quietly, as the brief asks.
4. **`ks_mandi_latest_date` in localStorage** (app only): the last price date shown. Needed for C6.
   `fetchMandiPrices()` asks "latest date" only when today has no rows, so after a visit on a day
   WITH rows the next day had nothing to fall back to offline. Zero extra requests.
5. **Freshness for other public data: 14 days** (not specified in the brief). MSP rows fall under
   it, so the official MSP table can still show while 8-day-old mandi prices are hidden (O6 checks
   the mandi table only).
6. **Spinner limit lives in the shared `Spinner`** (app only, lazy notice) rather than per page, so
   every data section — including pages not listed — is covered.
7. **Mic hidden in the app unless `/transcribe` works.** Android's WebView exposes a non-working
   `webkitSpeechRecognition`, so the app showed a mic that could never work. Found by S9.
8. **S6's location.** S6 takes one high-accuracy GPS reading in the page before pressing the
   Post page's own "use my current location" button. The button asks for a LOW-accuracy fix
   (10 s), which a freshly booted emulator only has after some app got a real fix. Recorded in
   `post.json`.
9. **S6/O2/O3 use Browse's "नई पहले" (newest first) button.** KSTEST listings from earlier runs sit
   at the same point, so in "nearest first" order the new one can be anywhere.
10. **S9 is NOT-RUN overall although all its checks passed.** The form's success state needs
    `SUPABASE_SERVICE_ROLE_KEY` in the function's env, which this batch may not use; the function
    answered 503 and the form showed its e-mail fallback (the documented failure state).
11. **The Devanagari check** (`scripts/test/v11_phase6.mjs`) already failed on this Windows machine
    before 8B (backslash paths vs its forward-slash allowlist). O8 records the script's exit and
    checks for NO NEW offender with paths normalised. The 4 genuine pre-existing offenders are
    PromoBento.jsx, termsContent.js, places.js, melaFormat.js.
12. **Harness environment handling** (no assertion changed by it):
    - a fresh emulator boot before each full run;
    - waiting for emulator internet after boot;
    - "System UI isn't responding" dialogs (the emulator's own System UI) answered "Wait" and
      counted in results.json — an ANR of OUR app would fail the run;
    - adb retries;
    - verified airplane mode;
    - WebView matched by process id (Playwright mislabels packages);
    - re-attach after a dropped CDP connection.
13. **Main chunk +4.9 KB** (94.5 KB vs 89.7 KB at the end of 8A; gzip +1.7 KB). Small hooks and
    policy constants are imported by `App`/`Spinner` (they do nothing on the web). The caching code
    itself is a separate chunk that the website never loads. O8 measured this in a temporary
    worktree of d165fbb; its note calls that "staging d165fbb" because the wording comes from T18.
14. **T7 / T9 assertion changes for prod**, both listed in P1:
    - T7: the /browse display part becomes NOT-RUN if a project has no listings near Sagar. Prod
      had listings, so it ran.
    - T9: added "the banner does not cover the NavBar". The simulated edge-to-edge check now expects
      the header directly below the banner (inset + banner height).
15. **The final staging meta run is the third.**
    - Run 1 surfaced harness timing issues (fixed).
    - Run 2 hit an emulator DNS outage: the first signup failed with `ERR_NAME_NOT_RESOLVED` and
      most later tests cascaded. Its results are kept locally in
      `logs/results-staging-run2-network-outage.json`.
    - The committed `results-staging-run1/run2.json` are both from the final run.

Open issues found:

- **Prod T14 flaked once** (run #2; run #1 passed). The keyboard was open (`mInputShown=true`) and
  the field focused and visible, but 1.5 s later the WebView had not resized yet (839 px of 915).
  T20 and P1 are RAN-FAILED as a result. Likely emulator lag; worth one look on a real phone.
- **S10 needed all 3 fix attempts** (WebView bounds read, System UI dialog, page still growing
  while measured). It passed in both final runs.
- **Pre-existing website bug — `/cold-storage`:** the list loads in `try/finally` without `catch`.
  A failed request becomes an unhandled "unknown" error and an empty list with no message (seen once
  against staging). Not fixed — that would change website behaviour; small fix for a web batch.
- **The Post page asks for a low-accuracy position with a 10 s timeout.** On a phone without a
  recent fix this can fail where a high-accuracy request would succeed. A website behaviour, not
  changed.
- **Profile shows the e-mail** (not the mobile) for e-mail-registered accounts; saving still needs a
  6-digit pincode (known issue, confirmed by S8).
- **Staging is filling up with KSTEST rows** (see section 6); every rerun of the staging suite adds
  2 accounts, 1 listing, 1 reveal, 1 profile edit and 1 feedback attempt (not stored).
- **The emulator (SwiftShader GPU) slowed down over hours** — System UI ANRs, a wedge needing a
  reboot. The meta runner now reboots it per run; a real device or a hardware-GPU emulator would be
  steadier.
- **`@capacitor/network` is used through dynamic import in three places** (banner, cache layer,
  back-online refresh). This is fine, but a later batch could centralise it.
