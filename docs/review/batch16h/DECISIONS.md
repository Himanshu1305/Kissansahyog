# Batch 16H decisions

- Data source unchanged: Open-Meteo free tier (non-commercial). The licence decision is an open item and is NOT part of this batch.
- New files only: `supabase/functions/_shared/weather-core.js`, `supabase/functions/weather-refresh/index.ts`, migration 0072 (+ rollback), two ship/rollback scripts, one unit test with a fixture and a golden file, these docs. Nothing under `src/` or `public/`, no change to `scripts/refresh-data.mjs`, the GitHub workflow, or `weather_cache_v2` columns/RLS.
- `weather-core.js` is a port of `refreshCell`, `computeSeasonRain`, `PILOT` and `gridKey`. One deliberate difference: hourly `time` text is IST wall-clock, so the "one hour before now" cut reads it as +05:30 (as `src/lib/weather/freshness.js` does). The GitHub job reads it in the runner's zone (UTC), which keeps hours that are really up to 5.5 h old; the site trims to "now" anyway, so the stored hourly list from the function simply starts at the right hour.
- `computeSeasonRain` takes the IST date as an argument (the original called `todayIST()` itself). Output is otherwise identical, including the `source` string (en dash written as `–` so the file stays ASCII).
- `limit`: the number of cells per forecast call, max 60 (larger values are cut to 60; non-integers and values below 1 are a 400). Pilot cells are always in the run, so the effective number is never below the 8 pilot cells (the staging probe with `limit: 2` therefore made 8 calls). Season mode: max 6.
- Order: pilot cells first, then the other cells, oldest `fetched_at` first and never-fetched first. With a limit smaller than the cell list the leftover cells rotate fairly from run to run (unit-tested).
- Cell list = PILOT + `weather_grid_requests` rows requested in the last 30 days (same rule as the GitHub job), de-duplicated by the cell centre (0.1 degree).
- Forecast writes use `upsert` on `grid_key` and never include `season_rain`: an existing season value stays, a brand-new row gets null. Proven on staging (hash of `season_rain` identical before and after) and by a unit test that also checks the function source has exactly one `.upsert(` and it uses `buildForecastRow`.
- Season mode updates only `season_rain` (`.update(...).eq('grid_key', ...)`), only for cells that already have a row, and adds a `computed_on` key (IST date). Readers of `season_rain` (`src/lib/weather/weatherApiV2.js` passes it through, `src/screens/Mausam.jsx` reads only `to_date_mm` and `normal_mm`) ignore unknown keys; `source`/`season_start` are not shown. A failed archive call leaves the old value in place.
- Season work is at most 6 cells per call, every 6 hours = at most 24 cells a day. With more than 24 requested cells some cells would be recomputed less than daily. The season value moves by a few mm a day, so this is harmless; if the cell list grows far beyond that, change the schedule/limit in a later batch rather than lowering anything silently. The summary field `cells_left_over_4h` is for the forecast list.
- Retries: 429 and 5xx and network errors/timeouts are retried up to 2 times (waits 1 s, 2 s); 429s are counted in `rate_limited`. Other 4xx stop at once. Concurrency 4 (season: 2), 150 ms between request starts, 15 s forecast / 30 s archive timeout, 100 s whole-call deadline (the pg_net timeout is 120 s). Cells not started when the deadline passes count as not written; pilot cells not written make `ok:false` (HTTP 502).
- The function logs only the summary line. Error lines carry cell key, error name/message/cause code with URLs cut out and any secret replaced; they never carry a URL or header.
- Guards are the 16E ones: constant-time `x-cron-secret` check (403), `EXPECT_PROJECT_REF` vs `SUPABASE_URL` (500), bad body (400).
- Migration 0072: first statement is a guard that raises a clear error if the Vault secrets `project_url` or `mandi_cron_secret` are missing (checked with dynamic SQL so a missing Vault extension also gives the clear message). It creates/deletes no secret. Forecast job `20 */2 * * *`, season job `40 */6 * * *` (UTC), pure ASCII.
- Ship script differs from 16E: no key typed, no secret made. It checks the NAMES of the two production function secrets (never values) and stops if one is missing. The "fire once" SQL and the check are two separate blocks (pg_net is asynchronous, so the reply is only readable a few seconds after the first block has run).
- Staging: `CRON_SECRET` was replaced by a fresh random value (the old one was only readable as a digest, and the proof needs to send it). `EXPECT_PROJECT_REF` was re-set to the staging ref. Staging `mandi-refresh` has no cron job, so nothing depended on the old value. The value was kept only in a temporary file outside the repo and then deleted.
- The Supabase connector refused SQL on staging ("You do not have permission to perform this action"), so the scheduler-path proof (Vault secrets, apply 0072 twice, real pg_cron fire, rollback) could not be run. It was not worked around. The migration is a copy of the proven 0071 pattern with a guard added; it is untested on a database. See PROBE_RESULTS.md.
- GitHub job: untouched. It stays a second writer and the watchdog (RED when the Sagar cell is older than 2 h after its own refresh).
