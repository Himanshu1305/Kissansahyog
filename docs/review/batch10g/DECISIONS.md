## Phase 1 — database (0065)

8. **Status values:** `disabled` added; constraint widened (`active, closed, removed, disabled`). Rollback moves `disabled` rows to `active` first.
9. **Seller toggle rules:** disable only from `active`; enable only from `disabled`; enabling an admin-disabled listing → `disabled_by_admin`; `closed`/`removed` → `invalid_state`; repeating the same action is a no-op (no error). `expires_at` is never touched (an expired listing stays expired).
10. **Admin disable from `active` or `disabled`** (an admin can take over a seller-disabled listing; it then becomes admin-disabled with a reason). Admin enable only from `disabled`; clears both admin marks. Reason required for disable and delete (trimmed, 1–300 chars), optional for enable (stored in the log if given).
11. **`delete_my_listing` is for the owner only — also for admins.** An admin deleting someone else's listing must use `admin_delete_listing` (reason + audit). Tested.
12. **Photo paths** come from `details.photo_urls`: only URLs of our bucket (`…/storage/v1/object/public/listing-photos/<path>`) are returned; any other URL is ignored. Helper `listing_photo_paths(jsonb)` (not callable through the API).
13. **Audit table `listing_admin_actions`:** admin id, listing id, action, category, reason, time — no listing text, no phone, no place. RLS on, no policies, no grants to anon/authenticated (the API cannot read or write it). Rows stay after the listing is gone (that is the point of the log).
14. **`admin_delete_listing` resolves open reports** on that listing as `removed` with the reason before the row delete (then `listing_id` becomes null by the FK). Closed/dismissed reports are left as they were.
15. **`get_my_listings` / `get_admin_listings` are dropped and recreated** (PostgreSQL cannot change a function's result columns in place). New columns are appended after the old ones; the default grants (incl. PUBLIC, as before) are kept, plus explicit anon/authenticated/service_role. Existing callers (the app, `scripts/test/*`) read by column name → unaffected.
16. **Advisors (staging, after 0065):** only the expected findings — the new SECURITY DEFINER functions are executable by anon/authenticated (the same WARN as the 129 existing RPCs; it is the `p_actor_id` model, BACKLOG), and `listing_admin_actions` has RLS with no policy (intended). `evidence/advisors-security-10g.txt`.

## Phase 2 — photo removal

17. **Option 1 does not work — proven.** A plain SQL delete of the `storage.objects` row (run as the database owner) is refused by Supabase's trigger `storage.protect_delete` ("Direct deletion from storage tables is not allowed. Use the Storage API instead.", HTTP 400 / 42501); the photo URL keeps answering 200. The guard can be switched off for one transaction (`storage.allow_delete_query`), but that drops only the metadata row and leaves the file bytes in the storage backend as an orphan — not "removed from the system" → rejected.
18. **Option 2 used, tightened to "only what a delete queued".** The delete RPCs put the returned paths into `public.listing_photo_deletions` (RLS on, no policies, not readable through the API). A new storage policy `listing_photos_queued_delete` allows DELETE in bucket `listing-photos` only when `public.listing_photo_deletable(name)` is true: the path was queued in the last 30 days AND no existing listing still lists it. The app removes the files with the normal Storage API right after the RPC succeeds. Proven on staging: an unrelated photo, and a photo of a still-existing listing, cannot be deleted by anon (API answers `[]`, file stays); the queued photos are removed, their storage rows are gone, and every uncached request for them answers 400. So the policy does NOT let "any anon client delete any object if it knows the path" — only objects of listings that were already deleted by their owner or an admin. Residual: anyone who learns such a queued path could delete it a moment earlier than the app does — the same file that is being deleted anyway.
19. **Interrupted removals are retried.** `get_my_pending_photo_deletions(actor)` returns queued paths that still exist for the person who queued them; My Listings (seller) and the admin listings panel retry them on load. Queue rows whose file is gone are dropped by the next delete call (housekeeping inside `queue_listing_photo_deletions`, which is not callable through the API).
20. **CDN window — HUMAN-REVIEW.** Photos are uploaded with `cache-control: 3600`. A photo that someone viewed shortly before the delete can still be served by Supabase's CDN edge for up to 1 hour (staging: plain URL 200 `HIT` right after the delete, every uncached request 400). A photo nobody viewed recently answers 400 at once. Re-checks: `evidence/photo-cdn-recheck.txt`. Option to shorten: lower `cacheControl` on new uploads (costs repeat downloads) → BACKLOG.
21. **Other copies.** `/listing/:id` is not prerendered and listings are in no sitemap or `public/search-index.json`. The prerendered homepage and `/jugaad` show the newest listing cards captured at build time; a deleted listing stays in that saved HTML until the next build/deploy (its link opens "विज्ञापन नहीं मिला", its photo no longer loads). The PWA service worker caches Supabase responses network-first (online it always asks the server; a phone that viewed the photo may show its cached copy only while offline, up to 24 h). WhatsApp share links point to `/listing/<id>` → "not found" after a delete.
22. **One migration file for production.** Section 6 of 0065 redefines the two delete functions to add the queueing; production gets the whole file once (`docs/review/batch10g/PROD_MIGRATION_0065.sql`, same text as `supabase/migrations/0065_listing_delete_disable.sql`), rollback `PROD_ROLLBACK_0065.sql`.
